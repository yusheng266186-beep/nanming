## 优先处理：P1

### R01 Redis 命令超时后，响应会错配给下一条命令

位置：`packages/ai-gateway/src/redis-client.ts:119-135`。超时只从 FIFO 删除等待项，未关闭连接；RESP 无请求 ID，迟到响应由 `onData` 交给当前队首。实测第一条 GET 超时后，第二条 GET 收到第一条的 `FIRST`。这会破坏共享会话、额度和 TOTP 原子操作的结果解释，影响不限于报错提示。应超时即销毁连接并拒绝该连接全部待处理项，重连后发送新命令；有副作用的操作仍须遵守既有幂等规则。补延迟响应、并发命令、断线重连测试。

### R02 开发服务器仍直接暴露真实学校数据目录

位置：`apps/web/vite.config.ts:82-85`。`serveDataDirectory` 默认挂载 `/data/quality-huixi` 到真实产物目录，GET/HEAD 没有姓名、查询码或限流校验；知道路径即可读索引/分片。当前只在开发服务生效，不能据此声称 Pages 已泄露；但开发机、局域网预览或代理暴露该端口时会绕过学校 API 的整个安全边界。应去掉真实目录的默认挂载，演示改用合成数据。无需请求真实分片即可从挂载和处理函数确认。进度文档“Vite 不再直接暴露”的原结论不符合代码。

### R03 六位 AI 动态码兑换没有失败尝试限流

位置：`apps/api/src/server.ts:213-245`。有效码有 Redis 防重放，但无效码直接 401，入口没有 IP/全局频率预算；后续会话额度保护不到认证入口。允许三个时间窗口增加了同一时刻可接受的码数。应在验证前执行共享限流、记录脱敏失败计数，并设定服务总预算。该结论针对应用代码；本轮没有验证云边缘是否另有保护，也没有对生产试号。

### R04 第一次选择登船口不会立即跳到定位

位置：`apps/web/src/App.tsx:551-555`。`setEntryChosen(true)` 后同一回调调用 `goTo('locate')`，后者仍捕获本次渲染的 `entryChosen=false` 和旧门禁。卡片关闭、入口状态更新，但本次跳转被拦；第二次点击或点导航才可进入。两条入口都有此问题。提取回调已复现旧状态读取；应把“选入口并跳转”作为原子动作，或在新状态提交后跳转，并加真实组件点击测试。

### R05 没有 AI 访问码时，宣称可用的无 AI 主流程走不完

位置：`apps/web/src/progress.ts:82-86`、`chapters/talk.tsx:166-190`、`App.tsx:508-521`。方向前必须 `chatted=true`；它只来自 AI 用户转录，而未连接时只有兑换码输入，不能发言，也无显式跳过。首次无访问码或兑换服务不可用时，学生无法继续自选专业/匹配/航线图。应提供明确的“跳过谈心，自己选方向”动作并纳入门禁；这不要求取消负责人规定的逐章顺序。

### R06 清空成绩来源后，旧探索区间仍然有效

位置：`apps/web/src/App.tsx:180-192`。自动派生 effect 在没有有效考试且目标分为 null 时不调用 `setRange(null)`。先填写目标分，再清空；或删除唯一有效考试且没有目标分，旧区间依然显示并使定位完成、池子可能仍被视作新鲜。提取回调已复现。应明确区间来源及失效规则，无有效来源时清空自动区间；若允许独立手填，必须单列来源而非沿用旧“自动生成”依据。

## 后续修复：P2

### R07 AI 收尾请求没有进入 pending，失败也被永久冻结

位置：`App.tsx:209-215,574-588`。`runFinalTurn` 没有置 `ai.pending=true`，学生仍能发新请求；新请求会推进 `aiSeq` 并丢弃收尾响应，同时 `finalTurnRef` 已置 true 不再触发。即使没并发，网络失败也无条件 `setFinalDone(true)`，后续建议被冻住。已用失败返回复现。需要独立收尾状态，成功才完成，失败可重试，并避免与普通发送并发。

### R08 清除探索没有重置全部状态，兑换响应还可能回写

位置：`App.tsx:251-285,379-396`；`chapters/talk.tsx:94-103`。清除不重置 `finalDone/finalTurnRef`，第二次探索不再自动收尾；章节内部 `summarySeen` 也跨探索保留。`exchangeCode` 没有序号或取消保护，若清除发生在兑换请求期间，迟到响应又写入 token；原清除时看不到该 token，无法撤销。应统一 exploration generation，清除覆盖所有会话/章节锁存状态，并让旧兑换结果失效。前者有源码探针，后者是调用链确认，未作生产请求。

### R09 AI 输入版本检查在实际 App 中没有读到响应时的新版本

位置：`App.tsx:416,580`；`ai-panel.ts:169-194`。发送时两次 `aiStamp()` 同时求值后作为普通对象传入，响应时两者仍相等；改选科/批次不会推进 `aiSeq`。在等待回复时修改输入，旧目录建议仍能并入当前状态。应在响应合并点通过 ref 读取当前 generation/catalog key，并用当前目录再次过滤；不要仅测试底层纯函数的两个手工不同参数。

### R10 过期院校池可以被导出成“新条件”的航线图

位置：`App.tsx:287-303`；`chapters/chart.tsx:74-99,249,532`。页面虽有 `poolStale` 提示，图本身使用当前 range/contextLabel，院校仍来自旧 pool；PNG 可保存且不带页面外的过期提示。JSON 同样混用新 form/range 与旧 routes。应禁止过期导出，或统一使用池子的条件快照并把过期状态嵌进文件内容；补改分后直接导出测试。

### R11 “全国通用”描述超出实际匹配覆盖

位置：`chapters/sail.tsx:260-262`、`packages/match-input/src/index.ts:98-103`、`reference-lines.ts`。界面明确称任何省份均可用，但当前招生、位次、省控线和 scenario 都按四川处理，没有省份输入。非四川学生会得到四川口径结果。可保留通用的自我探索能力，但成绩定位/招生入口应明确四川适用范围；不能用同一省的分数线替代全国。

### R12 学校限流的故障与校园出口策略不适合直接推广

位置：`apps/api/src/school-access.ts:69-70,104-118,142`。Redis 不可用会退回各实例内存计数，学校认证的共享防护降级；一个出口 15 分钟最多 120 次，成功也占次数，超过 120 名学生集中查询即受阻。代码只读 socket.remoteAddress，SCF 代理下是否为真实访客 IP 尚未核查，可能进一步合并用户。应对学校敏感入口明确故障策略，按可信代理边界获取来源（不能直接信任任意 X-Forwarded-For），实测校园 NAT 和多实例。

### R13 SSE 实际整包缓冲，心跳不能保活

位置：`apps/api/src/server.ts:262-270`、`packages/ai-gateway/src/gateway.ts:290,465,479`、`apps/web/src/ai-client.ts:206` 附近。服务端等待完整 `careerTurn` 后才写响应头和 frames；心跳只存数组。客户端又等待 `response.text()`，因此并非实时流式显示。长思考期间代理看不到心跳，断开风险仍在。若要流式，网关需逐帧输出并明确输出审核边界；若设计就是完整审核后一次返回，应改文档与超时设计，不以“SSE 心跳”声称已保活。

### R14 当前主入口没有使用已有匹配 Worker

位置：`App.tsx:460`、`journey-model.ts:244`；Worker 只在旧 `JourneyApp.tsx:310` 创建。App 直接调用 buildSchoolPool，异步取数据后仍在主线程执行 buildMatchResult；async 不会自动转后台。当前构建也没有 Worker 产物。大数据和低端手机存在主线程阻塞风险，本轮没有测手机延迟。应接回 Worker 或先量化长任务；文档原有“当前 Worker 区间匹配”已纠正。

### R15 就绪检查并未检验它声称的全部依赖

位置：`packages/ai-gateway/src/gateway.ts:150-158`、`apps/api/src/server.ts:209-211`。`public_data` 恒为 true，AI 就绪仅看配置/存储，不检查学校数据与真实上游，HTTP 始终 200。只看状态码会将不可用服务判为健康；不能用它证明 COS/千帆当前可用。应分离存活、依赖就绪和低频端到端探针，监控明确解读能力字段，失败时提供适当状态。

### R16 验证失败不阻断发布，且测试缺少实际组件时序

位置：`.github/workflows/deploy-pages.yml:45-52`、`nanhang-app/vitest.config.ts` 与前端测试目录。`continue-on-error: true` 是负责人此前授权的验收发布策略，不是擅自绕过；但它会持续用于后续 main 推送。许多界面测试只验证源字符串，无法发现 R04/R07/R08 的事件时序；全绿也不能代替组件测试。建议保留显式验收预览通道，正式发布恢复门禁；补少量真实交互与故障用例，CI 的数据测试使用合成 fixtures，不能为通过测试上传真实成绩。本轮未在干净 Linux 克隆重跑 CI，旧 CI 失败只作为历史。

### R17 客户端加载发布包缺少版本一致性及完整性校验

位置：`packages/release-loader/src/index.ts:124-148,172-177`。网络 JSON 直接断言类型，未校验 pointer.current 与 manifest.release_id、分片归属及预期内容哈希。错误上传/混版本数据可能仍被装配进结果；HTTPS 不能检查发布操作自身的错误。建议入口做 schema/ID/路径验证，分片对照发布端可信哈希；本轮未发现当前本机数据损坏，独立数据验证通过。

### R18 开发依赖存在已公布的中危问题

锁定 Vitest 3.2.7，官方 npm audit 给出 vitest 与 @vitest/mocker 两个 moderate 条目，实为同一 [维护者安全公告 GHSA-82fw-gwwq-j7x9](https://github.com/vitest-dev/vitest/security/advisories/GHSA-82fw-gwwq-j7x9)。修补线包含 4.1.11。影响为特定 mock 插件开发服务文件读取；当前 node 环境 `vitest run` 未证明满足远程利用条件，不能写成线上 API 已可被攻击。建议安排有回归测试的升级，不直接 `audit fix --force`。

## 需要完善但不冒充新漏洞的事项
