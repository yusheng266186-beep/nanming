## 每次修改的完成条件

一次有明确目的的修改（代码、配置、数据、部署、测试、文档或工具）必须在同一轮工作结束、暂停或交接前记录；连续编辑同一改动可以合并为一条，不要求每次按键留记录。即使失败、未完成或尚未提交，也要如实写“进行中/阻塞”，不能等到成功或下次对话才补。

1. 在 `docs/IMPLEMENTATION_LOG.md` 顶部追加：时间、修改目的、涉及文件/模块、实际成果、验证命令与结果、未完成项、下一步；文档专用修改也要记录。
2. 更新 `docs/PROJECT_STATUS.md` 与 `docs/project-status.json` 的核对基线、任务状态和下一步。进度未变应在记录中明确“任务状态未变”，不得为文档修改虚增完成任务。
3. 更新相关专题说明及 README 正文，删除或改写已失效的当前结论。新增决策写 ADR；不得擅自改冻结合同。
4. 在 `docs/VALIDATION_RESULT.md` 区分本次实测、历史记录和未验证；有新验证时保存脱敏日志。仅文档修改不要求无意义重跑全部业务测试，但必须跑文档一致性检查；没跑的检查注明没跑。
5. 在完整项目根目录执行 `py -3.12 tools/sync_project_docs.py --package`，随后执行 `py -3.12 tools/sync_project_docs.py --check`，必须通过后再报告完成。生成摘要、参考副本、索引、哈希与源码包不得手改。未通过时记录原因与后续动作，不得宣称交付包最新。

## 每次提交的要求

- 文档记录与对应修改必须进入同一次提交，包括相关生成文本；不能“先交代码、以后补文档”。源码 ZIP 按现有 .gitignore 留在本机，但仍须重新生成并校验。
- 提交前逐项检查暂存差异与记录是否对应，确认无密钥、学生姓名/成绩、验证码或私有材料混入；不得打包 `private/`、真实成绩产物、依赖及编译输出。
- 提交记录使用可识别的变更标题；文档可写本轮变更标识和修改前的业务 SHA。不要为了写入本次提交自身 SHA 反复补提交，也不要把旧 SHA 冒充当前 HEAD。
- 尚未获授权提交时，照常更新文档并明确“文档已同步，尚未提交”；本规则不自动授权推送或部署。
- 自动同步检查只保证受管文件、摘要、副本和包的一致性，不能证明正文语义或实际部署状态正确。每次仍须人工/Agent 对照源码、实际命令结果与产物核实。当前未安装 Git 提交钩子，不能声称已有强制拦截。

## 接手顺序

先读 `AGENTS.md`，再读 `docs/PROJECT_STATUS.md`、`docs/project-status.json`、实施记录最新条目与当前验证结果；随后检查 `git status --short`、最近提交和工作区差异。已有变更不得覆盖。只在核对后更新基线，优先处理已记录的下一步。

进度必须区分：已实现、已本地验证、已部署、已线上验收；数据包发布不等于站点上线，跳过不等于完成，历史成功不等于当前验证。暂停时注明剩余工作和复现/继续命令。
